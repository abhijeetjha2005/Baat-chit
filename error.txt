

5. message_deleted over WebSocket doesn't delete anything
In config/websocket.js, the message_deleted handler just re-broadcasts the event to all connected sockets — it never calls Message.findByIdAndDelete. The actual deletion only happens via the separate REST route (chat.controller.js). This happens to work today because the frontend calls the REST DELETE first and only then emits the WS event — but the WS handler itself will let anyone broadcast a fake deletion for a messageId they don't own, since there's no ownership check at all in that handler.

🟠 Medium — real logic bugs affecting behavior

6. Search box result never resets
Friends.jsx: when you type a search, the server's search_results replaces friendsList entirely. When you clear the search box, nothing re-fetches the full contact list — friendsList stays stuck on the last search's smaller result set forever.
Fix: when searchTerm becomes empty, re-send fetch_contacts_list, or keep the full list and search-results in separate state.

7. Messages can leak into the wrong open chat
Chatright.jsx, in the receive_message handler:

js
if (msgSenderId === receiverId || msgSenderId === currentUserId) { ...append... }

If you're chatting with Friend A but you send (or have sent, from another tab) a message to Friend C, msgSenderId === currentUserId is true and it gets appended to the currently open chat with A — even though it belongs to a different conversation.
Fix: also check data.conversationId === activeConversationId (or that receiverId matches) before appending.

8. send_voice WS handler will throw if receiverId is missing

js
const receiverSocket = activeUsers.get(receiverId.toString());

No optional chaining here, unlike the identical line in send_message (receiverId?.toString()). A malformed payload here throws and gets swallowed by the outer try/catch, silently failing.
